# A Brief Explanation of Cog

## What Cog Is

[Cog](https://github.com/nedbat/cog) is a small Python tool by Ned Batchelder
that lets you embed runnable code inside other files — usually Markdown — and
inline the output of that code into the surrounding text. It turns a document
into a small, runnable program whose rendered output is part of the source.

The pattern is called *literate programming-lite*: the document you read is
the source, but parts of it are computed, not typed.

## The Mechanics

You write code inside a pair of HTML-comment markers, and everything you
`print` (or anything written to stdout) replaces the closing marker on the
next run:

```markdown
The current version is:
<!-- [[[cog
import cog, importlib.metadata
v = importlib.metadata.version("cog")
cog.out(f"**{v}**")
]]] -->
<!-- [[[end]]] -->
```

Running `cog -r README.md` (or just `cog`) executes the block and rewrites the
file with the printed text replacing the `end` marker.

Three flags cover almost every workflow:

| Flag | Purpose |
| --- | --- |
| `cog -r FILE` | Re-render the output in place |
| `cog -d FILE` | Delete the rendered output (useful for clean diffs) |
| `cog --check` | Exit non-zero if output is stale — wire into CI |

## Why It Is Useful

The main reason to reach for Cog is **single source of truth**. Hand-maintained
docs drift the moment reality changes. Cog lets the doc *compute* values from
the real source instead of copying them:

- Version numbers and badges pulled from `pyproject.toml`.
- Tables of CLI flags introspected from `argparse` definitions.
- API endpoint lists generated from a router module.
- Diagrams rendered by Graphviz/Mermaid at doc-build time.
- Repo indexes — for example, the auto-generated list of projects in this
  repository's root `README.md`, which is regenerated by Cog on every change.

When the source changes, `cog -r` refreshes the doc. When you forget to run
it, `cog --check` fails CI. That feedback loop is the whole pitch.

## How This Repo Uses It

The root [`README.md`](../README.md) is **not hand-edited**. It is rendered
from a Cog block that, on each run:

1. Enumerates every top-level subdirectory and looks up the oldest commit
   date for each via `git log --diff-filter=A`.
2. Sorts the projects newest-first and renders a heading and a summary for
   each. The summary is read from a cached `_summary.md` if present, and
   otherwise generated by piping the project's `README.md` into the `llm`
   CLI (`github/gpt-4.1`); the result is then cached to `_summary.md` so
   subsequent runs are instant.
3. Stamps a standard `<!-- AI-GENERATED-NOTE -->` disclaimer into each
   project's `README.md`.

The `_summary.md` files in each subdirectory are a deliberate seam — they
let the maintainer audit or override an individual summary without
re-running the LLM, and they keep regenerations cheap.

## When Not To Use It

Cog is intentionally minimal. If you need cross-references, navigation,
search, or a proper doc site, reach for MkDocs, Sphinx, or a Jupyter-based
pipeline. Cog is the right tool when you want a single file whose visible
content is a function of the rest of your repo, and you'd rather not
introduce a build system to make that happen.
