Dynamic subagents

You know the task tool: the model delegates to a subagent one tool call at a time. Dynamic subagents let the model write a short JavaScript program that dispatches subagents in loops, branches and parallel batches. This page explains the feature, where it pays off, what broke when I tested it, and whether it's really "the same as Claude Workflows".

Claim checked "Dynamic subagents are like Claude's workflows: deterministic workflows chained together." Partly true.

The core idea is the same. A model writes JS, and the code (not the model) fans out and chains subagents. In both systems only the control flow is deterministic; what the subagents return is not. In deepagents the coordinator rewrites the script on every request, and the two runtimes handle failures, schemas, resume, reuse and opt-in differently. See the comparison.

The idea

From the task tool to task()

With plain subagents, every delegation is a model turn. The model can emit a batch of task calls at once, but that batch is fixed when emitted: nothing can loop, branch on a result, or retry without another model turn, and every result lands in the model's context. Dynamic subagents move that orchestration into code that runs inside one eval tool call.

Setup

Two ingredients: subagents and an interpreter

Add CodeInterpreterMiddleware from langchain-quickjs. It gives the agent an eval tool backed by a QuickJS sandbox (no filesystem, network or clock). Because the agent has subagents, the sandbox also gets a task() global. Nothing else changes in your create_deep_agent call.

# pip install "deepagents[quickjs]"
from deepagents import create_deep_agent
from langchain_quickjs import CodeInterpreterMiddleware

agent = create_deep_agent(
    model="anthropic:claude-sonnet-5",
    subagents=[
        {"name": "bug-fixer",       "description": "Investigates bug reports",      "system_prompt": ...},
        {"name": "feature-analyst", "description": "Rates feature effort and impact", "system_prompt": ...},
        {"name": "support-agent",   "description": "Answers how-to questions",       "system_prompt": ...},
    ],
    middleware=[CodeInterpreterMiddleware()],   # task() is on by default when subagents exist
)
agent.invoke({"messages": [{"role": "user",
    "content": "Run a workflow that triages these tickets: ..."}]})

You don't write the orchestration; the coordinator does. Below is the script my Sonnet coordinator actually wrote for a 6-ticket triage (trimmed). It classifies every ticket in parallel, then routes each one to a specialist by its label.

const specialist = { bug: "bug-fixer", feature: "feature-analyst", question: "support-agent" };

const cls = await Promise.all(tickets.map(async ([id, text]) => {
  const r = await task({
    description: "Classify this support ticket as exactly one of: bug, feature, question.\nTicket: " + text,
    subagentType: "general-purpose",
    responseSchema: { type: "object", properties: { category: { type: "string", enum: ["bug", "feature", "question"] } } },
  });
  return { id, text, category: r.category };
}));

const out = await Promise.all(cls.map(t =>
  task({ description: "Handle " + t.id + ": " + t.text, subagentType: specialist[t.category] })));
out.join("\n");   // last expression = what the model sees

task() takes description, subagentType (a name you registered) and an optional responseSchema. Each call runs that subagent's full agent loop and resolves to its final answer.

Where it's useful

Shapes of work that suit it

The coordinator picks a shape from the task; none of this is configuration. The docs list these patterns, and I tested each shape with scripted runs.

items → N workers → merge

Fan-out and synthesize

Review every file in a directory, every log, every service. Code covers all of them; a model choosing calls tends to sample.

classify → route by label

Classify and act

Ticket triage, error buckets, feedback. Send each item to the specialist that fits its label.

find → verify × k → vote

Adversarial verification

Security or compliance findings where a false positive is costly. Keep only the claims that independent verifiers confirm.

N drafts → score → best

Generate and filter / tournament

Architecture options, rewrites. Compare candidates in code or with a judge subagent, bracket by bracket.

while (new results)

Loop until done

Dead-code sweeps, dependency audits: anything where you don't know the size up front. Dedupe in JS and stop when a round finds nothing new.

variables persist

Multi-turn working sets

With mode="thread", results from turn 1's workflow are still in scope in turn 2, so the agent can refine without re-running.

Skip it for one or two delegations; a plain task call is simpler. Saying "workflow" in the prompt nudges the coordinator toward this path. In my runs it reached for eval even without that word, but then classified the tickets itself and fanned out only once.

Tested, deepagents 0.7.23 · langchain-quickjs 0.3.8

What I saw when running it

Mechanics were measured with scripted fake models (fixed delays, so timings are exact). Model behaviour was measured with real Claude models: Sonnet as coordinator and Haiku as subagents.

works

Parallelism is real, and capped at 32

8 one-second subagents finished in 1.01 s. 40 of them peaked at 32 concurrent and took two waves. Results come back in input order.

works

The 5 s timeout only counts JS CPU time

A busy loop is killed at 5 s. Eight sequential one-second subagents (9 s total) ran fine, because waiting on subagents doesn't count.

works

Same script, same dispatches

The classify→route script run 3 times gave identical results and identical sets of dispatches. Only the start order varied.

works

The coordinator repairs its own workflow

When stage 2 came back empty, the coordinator wrote a second eval that reused the cls variable still in the REPL and re-ran only stage 2.

works

Interrupts resume without redoing finished work

One of 4 subagents called a human-in-the-loop interrupt(). After Command(resume=…) only that subagent continued; the 3 finished siblings were not re-run. This needs a checkpointer. Siblings still running when the interrupt landed do re-run.

gotcha

One failure discards the whole batch

A throwing task() inside Promise.all turns the entire eval into an error, even though the siblings finished and their results are thrown away. Promise.allSettled keeps partial results, but the error text becomes HostError: Host function failed.

gotcha

A typo in subagentType doesn't throw

task() resolves to the string "We cannot invoke subagent … does not exist", which then flows on as if it were a real answer.

gotcha

responseSchema is a request, not a guarantee

If the subagent ends without structured output, task() returns its plain text and r.outcome is silently undefined. This is what emptied stage 2 in the real run.

gotcha

Approvals don't apply per dispatch

task() runs inside an already-approved eval, so the parent's interrupt_on doesn't fire for each subagent. Gate eval itself if you need sign-off.

gotcha

The script differs every run

The same prompt twice produced the same overall shape with different code. Without the word "workflow", the coordinator produced a different plan (1 stage, 13 dispatches instead of 18). The structure is chosen at run time; nothing is a fixed pipeline.

The claim

Is it the same as Claude Code Workflows?

I ran the same triage as a Claude Code Workflow: 4 tickets, classify then route, 8 Haiku agents. Same family, different runtimes. Claude's script runs as a background job with a journal; deepagents' script runs inside one tool call of the agent's loop.

So "similar" is fair for the idea and the patterns. "Deterministic workflows chained together" is misleading for both: the control flow is code, but the subagents are still models. In deepagents the code itself is new on every request.

If you adopt it

Guardrails I'd add

  • Tell the coordinator (in your system prompt) to use Promise.allSettled or a per-call .catch, so one bad item doesn't discard a 30-item batch.
  • Check structured fields in JS before using them. Treat a string result from a schema call as a failure.
  • Treat a result containing "does not exist" as an error.
  • Add a checkpointer if any subagent can interrupt. That's what makes resume skip finished work.
  • Put approval on the eval tool if subagents can do anything costly. Per-dispatch approvals won't fire.
  • Watch the custom stream for {type: "subagent", phase: "start" | "complete" | "error"} events to show a live fan-out view.
